# Москва ↔ Вьетнам: мониторинг авиабилетов

Python-бот ищет полные поездки Москва ↔ Нячанг / Дананг и после каждой успешной проверки присылает распределение цен в Telegram, а также сообщает о новых выгодных вариантах или снижении цены уже отправленного варианта. Запуск — GitHub Actions каждые два часа, без отдельного сервера.

## Настройки

Все параметры поиска находятся в `config.yaml`. Откройте файл на GitHub → Edit → измените значения → Commit changes. Следующий запуск применит их автоматически. Для немедленной проверки: Actions → flight-price-monitor → Run workflow.

По умолчанию:

- Вылет из Москвы с **1 марта по 28 апреля 2027 включительно**. Прилёт обратно в Москву — **не позже 28 апреля 2027**, по московскому времени (`return_end`). Поздние вылеты отсеиваются требованием пребывания 10–15 дней.
- Пребывание во Вьетнаме **10–15 календарных дней**, от местной даты прилёта до местной даты обратного вылета.
- Независимые билеты: пересадка от 6 до 48 часов в обе стороны. При смене или неизвестном аэропорте — минимум 12 часов.
- Максимальная длительность каждого билета — 36 часов, включая внутренние пересадки. Эта граница также используется для расчёта месяцев поиска обратных билетов.
- Пороги полной поездки — из `project_context.md`. Для Хошимина, где порог не задан, выбран редактируемый ориентир 32 000 ₽.
- Хабы Ханой, Бангкок, Алматы, Ташкент, Гуанчжоу, Гонконг, Хошимин включены для направлений из контекста. Дубай, Дели, Куала-Лумпур, Сингапур и Бишкек включены для обоих городов; их пороги 33 500 ₽ RT — предварительные ориентиры. Алматы остаётся включён для Нячанга.

`routes` задаёт направление, необязательный `hub`, `max_total_price` и `direct_only`. Последнее означает отсутствие внутренних пересадок у каждого приобретаемого билета. У маршрутов Москва–Нячанг и Москва–Дананг без заданного хаба есть поиск с разрешёнными внутренними пересадками. Для Нячанга также сохранён отдельный поиск прямых рейсов; оба варианта имеют порог 31 000 ₽ RT. Для нового маршрута через дополнительный хаб скопируйте строку, задайте уникальный `id`, город назначения и порог. При добавлении города укажите его IATA-код, название и IANA-часовой пояс в `cities`.

## Логика

1. Получить предложения для каждого направления и месяца; повторяющиеся запросы использовать из памяти текущего запуска.
2. Нормализовать время с учётом часовых поясов. Пропустить истёкшие предложения, неизвестные длительности, время без часового пояса и некорректные данные. Сохранить разные рейсы в один день.
3. Для маршрута с хабом проверить все четыре билета: Москва → хаб → Вьетнам и Вьетнам → тот же хаб → Москва. Проверить обе пересадки по абсолютному времени и длительность пребывания по местным датам.
4. Для маршрутов без заданного хаба проверить пары односторонних билетов и готовые тарифы RT (единая цена туда-обратно). Цена RT не удваивается. Комбинации двух тарифов RT через хаб и разных хабов туда/обратно пока не собираются.
5. Собрать статистику всех совместимых поездок независимо от цены. Сравнить полную стоимость с порогом включительно. Отдельные ценовые пороги на плечи не применяются.
6. Отправить до `max_alerts` самых дешёвых новых/подешевевших комбинаций. В ключ входят маршруты, аэропорты, время и рейсы; цена и изменчивые ссылки в ключ не входят.

Отправленная цена сохраняется только после подтверждения Telegram, отдельно после каждого сообщения. Более дорогой повтор той же комбинации не уведомляется. Варианты сверх лимита остаются для следующих запусков. `--dry-run` ничего не записывает. При повреждении состояния запуск завершается ошибкой, чтобы не вызвать массовые повторы. Если Telegram принял сообщение, но процесс оборвался до записи состояния, при следующем запуске возможен повтор.

## Отчёт после каждой проверки

Даже при отсутствии выгодных поездок бот отправляет таблицы по всем включённым маршрутам. Снаружи показываются маршрут, минимальная цена RT и даты. Распределение, подробности и ссылки находятся в раскрываемых цитатах Telegram. Пустые маршруты собраны в одном раскрываемом списке. Длинный отчёт разделяется по длине отображаемого текста, без учёта скрытых URL и HTML-тегов; ссылки сохраняются целиком. Диапазоны цен: до 5 тыс. ₽ включительно, затем шаг 5 тыс. ₽ до 50 тыс. ₽, всё свыше 50 тыс. ₽ — одной строкой. Нижняя граница не включается, верхняя включается, поэтому ровно 35 000 ₽ относится к 30–35 тыс. ₽. Строки, в которых все три значения нулевые, скрываются. Если по маршруту вообще нет вариантов, выводится одна строка.

Колонки:

- **Туда** — полные варианты Москва → Вьетнам. Через заданный хаб это сумма двух совместимых плеч. Дата вылета в заданном окне; после прибытия должно оставаться хотя бы минимальное число дней до крайней даты возврата.
- **Обратно** — полные варианты Вьетнам → Москва с прилётом до `return_end` включительно. Вылет не раньше начала окна плюс минимальная длительность пребывания.
- **RT** — полные поездки туда-обратно с проверенными датами, пересадками и пребыванием 10–15 дней, плюс готовые тарифы RT. Ценовой порог на эту статистику не влияет.

Для Нячанга и Дананга `max_transfers_by_destination: {CXR: 1, DAD: 1}` ограничивает каждую сторону одной пересадкой, включая пересадку между отдельными билетами и внутренние пересадки готового тарифа. Ограничение применяется и к статистике, и к уведомлениям.

Односторонние варианты могут не иметь подходящей пары. Готовые тарифы RT входят только в RT-колонку: их цена не делится на выдуманные цены туда/обратно. Для каждой колонки показываются количество и минимум. Это количество предложений/комбинаций в кеше, не число доступных мест. Один рейс может участвовать в нескольких полных поездках. Таблицы разных маршрутов могут пересекаться (например, прямые рейсы и поиск, допускающий пересадки), складывать их количества нельзя.

В каждом маршруте отчёт показывает самый дешёвый совместимый RT независимо от порога: цену, длительность пребывания, даты и местное время каждого плеча, аэропорты и ссылки API. Для отдельных билетов — ссылка на каждое плечо; для готового RT — одна общая ссылка без искусственного деления цены. При отсутствии ссылки это отмечается явно.

Отчёт отправляется заново в каждом успешном запуске, даже если цены не изменились. Отдельные выгодные предложения сохраняют прежнюю защиту от повторов. При сбое API на отдельном маршруте остальные проверяются: приходит отчёт с пометкой «неполный» и ошибкой у проблемного маршрута. Данные незавершённого маршрута не выдаются за отсутствие билетов. После отправки доступных результатов и сохранения истории запуск завершается с ошибкой, чтобы сбой был виден в Actions. `--dry-run` печатает отчёт без отправки.

## Ограничения источника

[Официальная документация Travelpayouts](https://support.travelpayouts.com/hc/en-us/articles/203956163-Aviasales-Data-API) описывает `prices_for_dates` как цены из поисков пользователей за последние 48 часов. Это кеш, а не проверка доступности всех билетов в реальном времени. Односторонние результаты группируются по дате: API может не вернуть другой рейс того же дня, который подошёл бы для пересадки. Пустой результат означает отсутствие подходящих данных в кеше, а не отсутствие рейсов.

Бот проверяет совместимость предложений, полученных в одном запуске. Одновременное наличие всех билетов при покупке, багаж и окончательная цена требуют проверки по ссылкам. Для готового RT API не сообщает отдельные аэропорты и перевозчика обратного плеча; бот не выдумывает эти данные. Цена рассчитана на одного пассажира, без добавления услуг.

## Локальный запуск

Python 3.11+:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Заполните .env своими токенами.
python monitor.py --check-config
python -m unittest discover -s tests -v
python monitor.py --dry-run
python monitor.py
```

`--check-config` не требует токенов и не обращается к сети. `--dry-run` требует только Travelpayouts token, получает реальные данные, печатает уведомления без отправки и сохранения состояния.

## GitHub Actions

Добавьте в Settings → Secrets and variables → Actions:

- `TRAVELPAYOUTS_TOKEN`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHAT_ID`

Сначала напишите своему боту `/start`. Workflow выполняет тесты, проверяет конфиг и запускает монитор. Расписание в `.github/workflows/monitor.yml`: `0 */2 * * *` (UTC). Расписание GitHub Actions работает на основной ветке и может запускаться с задержкой.

Файлы `data/alerts.json` и `data/history.json` коммитятся обратно. Нужны права workflow на запись; правила защиты ветки также должны допускать этот коммит. Шаг сохранения выполняется и при ошибке мониторинга, чтобы сохранить уже подтверждённые отправки. История ограничена последними 1000 запусками; старые записи прежнего бота сохраняются до естественного вытеснения. Не запускайте одновременно локальный монитор и Actions с общим состоянием.

Токены хранятся только в `.env` (игнорируется git) или GitHub Secrets. Для отдельного локального состояния можно задать `DATA_DIR`.

Для Бишкека используется актуальный код `BSZ`; старый `FRU` API больше не принимает. Идентификаторы конфигурации `fru-cxr` и `fru-dad` сохранены для непрерывности истории; в запросы передаётся `BSZ`.

В конце каждого отчёта после отдельных выгодных уведомлений приходит «🏆 Топ-5 по цене»: три независимые подборки — туда, обратно и RT, максимум по пять вариантов в каждой. Сортировка по полной цене выбранной категории, без ценового порога; повторяющиеся варианты из разных поисков объединяются. Указаны маршрут, даты и ссылки (на каждое отдельное плечо либо одна ссылка на тариф RT). Односторонние варианты не гарантируют подходящую обратную пару, RT-тарифы в односторонние подборки не включаются. Если данных меньше пяти, показываются все имеющиеся; сбойные маршруты в рейтинг не входят.
